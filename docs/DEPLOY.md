# Deployment runbook

How to ship Custom Color Palette for Google Workspace Docs, Sheets & Slides and run its config service + monitor. Read
`docs/plan.md` and `CLAUDE.md` first.

## What ships where

| Piece | Where | How |
| --- | --- | --- |
| extension (repo root) | Chrome Web Store **or** Workspace force-install | unpacked dir → packed `.zip` |
| `service/` | your box (Pi 5 / DigitalOcean) | FastAPI behind HTTPS |
| `monitor/` | your box / GitHub Actions | scheduled `npm run monitor` |

The extension works fully on its packaged defaults; the service + monitor are
optional infrastructure that add remote config and breakage detection.

## Extension: pre-ship checklist

- [ ] `npm run typecheck && npm test` green (the pre-commit gate).
- [ ] Manual release-gate pass in `docs/TEST_PLAN.md` (Tier 3) — load unpacked,
      confirm a brand color applies in Docs, Sheets, and Slides, and the popup +
      options + feedback page open.
- [ ] Permissions are still minimal: `storage`, `alarms`, and host access to the
      three `docs.google.com` editor surfaces only. Any addition must be
      justified in `docs/PRIVACY.md` and `CHANGELOG.md` (see "Documenting
      access-affecting changes" in CLAUDE.md).
- [ ] `CONFIG_BASE` in `config/endpoints.js` is set for the deployment
      (empty = packaged defaults only) and its origin is in `host_permissions`.
- [ ] **Icons**: `icons/` (16/48/128) ship and are referenced in
      `manifest.json`. The brand palette-stripe mark generated by `npm run
      icons` IS the shipping icon (decision 2026-08-09) — it matches the
      adaptive toolbar repaint. Regenerate if the default palette's leading
      colors ever change.
- [ ] `version` bumped per the semver rules in CLAUDE.md (every CWS upload needs
      a higher `version` string; burned numbers can't be reused).
- [ ] **Leave `key` in `manifest.json` alone.** It is the Chrome Web Store
      item's own public key, and it pins the extension's ID to
      `hchpnnppgakgmobkbldgkohmplkcahjl` for unpacked loads too. Without it an
      unpacked build's ID is derived from the FOLDER PATH it was loaded from,
      so it differs per machine and per checkout — which made enterprise policy
      untestable against a dev build, since Admin console policy is delivered
      per ID and the console can only target IDs that exist in the Web Store
      (see `docs/TESTING-0.2.0.md` C0). The store injects this identical field
      into what it distributes, so shipping it changes nothing about the
      published item. If a future upload ever objects to it, removing the line
      for that upload is safe — the store assigns the ID from the item, not
      from the manifest — but put it back afterwards.

## Chrome Web Store

1. Pack: `npm run package` → `dist/custom-color-palette-<version>.zip`
   (manifest at the zip root; `dev-reload.js` + `__tests__` excluded; the script
   prints the contents to verify).
2. Chrome Web Store Developer Dashboard → new item → upload the zip.
3. Listing: paste from `STORE_LISTING.md` (name, summary, description,
   permission justifications, data-usage answers) and the privacy disclosure
   from `docs/PRIVACY.md`. The privacy policy is published live at
   https://raylytics.io/brandpaletteinjector/privacy — paste that into the
   Privacy tab's "Privacy policy URL" field. Work the `LAUNCH_CHECKLIST.md` gate.
4. **Remote-code note for review:** the extension fetches *configuration data*
   (selectors + palette JSON), never code. The consuming logic is packaged and
   reviewed; only data is hot-swappable. State this explicitly to avoid a
   "remotely hosted code" rejection.

## Enterprise force-install (recommended for org rollout)

**An admin never runs a script.** Everything in this section happens in a web
UI — the Google Admin console — and only Workspace administrators can reach it,
because Google enforces that, not us. This is the platform-standard mechanism
for all Chrome extension policy: Chrome's managed storage area is read-only to
the extension, so there is no way for the extension to offer its own
admin-only editor, and nothing it could check to know who is an admin.
`dev/test-policy.sh` and the macOS plist recipe further down are **developer
tooling for testing this repo** — they simulate locally what Google's servers
deliver, and are not part of any admin's workflow.

End users install nothing; the palette simply appears. Via the Google
Admin console (Devices → Chrome → Apps & extensions) or a Chrome
`ExtensionInstallForcelist` policy, pin the extension ID to force-install on
managed browsers. Pair with a managed `CONFIG_BASE` so the central team palette
is pushed from `service/`.

### Pushing the brand palette to staff (no server needed)

This is the answer to "can I distribute the colors the way I distributed the
extension?" — yes, from the same Admin console page, with no service to host.
The extension declares an enterprise policy schema
(`config/managed-schema.json`, wired via `manifest.json`'s
`storage.managed_schema`), which is what makes the policy field appear in Admin
console at all.

> **Not comfortable hand-writing JSON? Don't.** `options/policy-builder.html`
> is a single self-contained page: pick the colors visually,
> choose one palette or several, tick the enforcement box if you want it, and
> copy the exact payload for the box in step 3 below. It runs entirely in the
> browser with no server and no permissions, it validates as you go (a bad hex
> or a nameless color is called out rather than silently dropped), and its
> output is checked against this extension's own policy reader by
> `options/__tests__/policy-builder.test.js`.
>
> **Getting to it.** An administrator who has the extension opens it from
> **Settings → Administrators → Build organization colors**; that is the
> primary route and needs nothing else. For an administrator who does NOT have
> it, publish `options/policy-builder.html` **and `options/policy-builder.js`**
> together next to the privacy page and send the URL, or send both files. It is
> two files rather than one because Manifest V3 forbids inline script on
> extension pages, so the logic must live in its own file — still no server and
> no build step, which is what matters. Working in this repo, double-click the file, or run
> `npm run policy:builder` for the `file://` URL. Note the npm script is
> developer convenience only: a repo-relative path is not something a browser
> can resolve, and no admin — and no tester following
> `docs/TESTING-0.2.0.md` — should ever be asked to run a command.

**Admin steps** (the standalone, hand-to-an-admin version of these, with the
field-verified console gotchas and a screenshot list, is `docs/ADMIN_GUIDE.md`)

1. In the Google Admin console, go to **Devices → Chrome → Apps & extensions →
   Users & browsers**, and select the org unit the staff are in.
2. Find **Custom Color Palette for Google Workspace Docs, Sheets & Slides** in
   the app list. **A new organization's list is empty**, and the extension does
   not appear there just because someone installed it — an admin has to add it:
   click the **yellow + button** (bottom right) → **Add from Chrome Web Store**
   → search `Custom Color Palette` → click the extension → **Select**.
   Use the Web Store option, **not** *Add Chrome app or extension by ID*: that
   one is for extensions you host yourself and will ask for an installation URL.
   (Field-tested 2026-08-24; the by-ID path is a dead end here and was the
   first thing a real admin hit.)
3. Click the extension's row to open its panel, and confirm the ID reads
   `hchpnnppgakgmobkbldgkohmplkcahjl`. Policy is delivered **per extension ID**,
   so an entry with any other ID silently configures nothing.
4. Decide the installation policy on that panel. **Force install** puts the
   extension on every managed browser in the org unit; **Allow install** lets
   staff install it themselves. **Force install is the expected production
   setting** — an org publishing brand colors generally wants the extension on
   every managed browser, not waiting for each person to add it.

   Either one delivers the palette policy below: the payload is attached to
   the extension ID, not to the installation. That is not just an assumption —
   nothing in the shipped extension reads `chrome.management` or `installType`,
   so it has no way to behave differently depending on how it arrived, and a
   static test (`options/__tests__/options-glue.test.js`) fails the build if
   anyone adds such a branch. Allow install has additionally been confirmed in
   the field (2026-08-24): policy arrived with `Source: Cloud`, `Status: OK`.

   What force install DOES change is everything around the extension: it
   installs automatically, cannot be removed by the user, and takes precedence
   over a locally loaded copy of the same ID. That last point is what makes it
   awkward to exercise against a development build — see "Testing the FORCE
   INSTALL path" below.
5. Scroll to **Policy for extensions** and paste the JSON below, edited to your
   brand colors. Then click **SAVE in the upper right of the settings panel** —
   the console does not put it next to the field you just edited, and nothing
   takes effect until you click it. The field turns yellow when you edit it and
   *stays* yellow after saving: that highlight means "set at this org unit",
   not "unsaved". To confirm a save stuck, reload the page and check the JSON
   is still there.
6. Delivery is not instant. On a staff browser, open `chrome://policy`, click
   **Reload policies**, and confirm the keys appear under the extension's
   section with status OK. Allow a minute or two before concluding anything.

```json
{
  "palette": {
    "Value": [
      { "name": "Poppy",    "hex": "#FE5917" },
      { "name": "Sunshine", "hex": "#EABF26" },
      { "name": "Grass",    "hex": "#385834" }
    ]
  }
}
```

Names appear on the swatch tooltip; `hex` must be a six-digit hex color. Up to
24 colors (`MAX_SWATCHES`). Entries with an invalid hex or a blank name are
skipped rather than breaking the rest of the palette.

### Publishing SEVERAL palettes (`palettes`, 0.2.0+)

One palette is not always enough — sub-brands, product lines, a retail and a
wholesale identity. Use `palettes` instead of `palette` to publish named ones:

```json
{
  "palettes": {
    "Value": [
      {
        "name": "Retail",
        "swatches": [
          { "name": "Poppy",    "hex": "#FE5917" },
          { "name": "Sunshine", "hex": "#EABF26" }
        ]
      },
      {
        "name": "Wholesale",
        "swatches": [
          { "name": "Grass", "hex": "#385834" },
          { "name": "Night", "hex": "#1A2D27" }
        ]
      }
    ]
  }
}
```

- **Both settings are supported, permanently.** `palette` is the single flat
  list above and existing deployments keep working untouched. Set `palettes` and
  it takes precedence; set neither and there is no org palette.
- **Staff start on the first one.** Up to 12 palettes (`MAX_PALETTES`); the
  order you write them in is the order staff see.
- **An entry needs a name and at least one usable color.** One with neither is
  dropped rather than shown as an empty choice, and the rest still publish.
- `paletteLocked` works the same way with either setting: it enforces the
  organization's colors, whichever of the two you used to publish them.

**What staff see.** The org palette becomes their **default** Brand row, and
policy updates apply live: change the JSON in Admin console and the next picker
they open shows the new colors, with no browser restart.

**The one caveat worth telling your staff.** Policy never overwrites colors a
user chose for themselves — and "chose for themselves" means *any* edit in the
popup or the settings page, including changing a single hex or deleting one row.
The popup auto-saves, so one tweak keeps a personal copy of the palette and
**that user stops receiving your updates** until they undo it. Both surfaces say
so when a policy is active: the popup shows "Use organization colors" and the
settings page's **Palette** selector offers the *Organization colors*
entry (Reset restores their last SAVED colors, not the org's). If a rollout
looks like it skipped someone, that is almost always why.

**Verify a rollout.** On a managed machine, open `chrome://policy`, click
**Reload policies**, and confirm the extension's `palette` policy is listed with
status OK. If the value shows a conflict or parse error, the JSON does not match
the schema — check that every entry has both `name` and `hex` as strings.

### Enforcing the palette (`paletteLocked`, 0.2.0+) — the usual choice

**Publish this unless you have a reason not to.** Field feedback (2026-08-25):
enforcement is what an administrator normally means by "these are our brand
colors", and the unlocked form surprises people — it publishes colors any user
can quietly edit away from, so a fleet can drift off-brand without anyone
seeing it happen. `options/policy-builder.html` ships with the box
ticked for the same reason.

The unlocked form is still right when teams are trusted to deviate and you want
your palette to be the convenient starting point rather than the rule.

Without `paletteLocked` the org palette is a **starting point**: staff can
personalize it, and doing so detaches them from your later updates. Add
`paletteLocked` to make it binding instead:

```json
{
  "palette": {
    "Value": [
      { "name": "Poppy",    "hex": "#FE5917" },
      { "name": "Sunshine", "hex": "#EABF26" },
      { "name": "Grass",    "hex": "#385834" }
    ]
  },
  "paletteLocked": { "Value": true }
}
```

What staff see under a lock: your colors become the palette they start on, in
every picker. The org palette itself is uneditable in both the popup and the
settings page, with a note saying so, and the Add / Reset / Save / Import
controls are hidden while it is showing, because every one of them ends in a
change that could not take effect.

They are NOT shut out of colors of their own. A Palette selector appears
listing your palettes alongside any of theirs, and they may switch to their own
and edit those freely; enforcement makes your palette the default and keeps it
uneditable, it does not forbid personal colors. This is deliberate (bd
`workspace-custom-palette-cv2`). If you need staff to have no other option at
all, that is not what `paletteLocked` does today - say so and it can be
reconsidered as a separate policy rather than by widening this one.

Three things worth knowing before you turn it on:

- **It is reversible and non-destructive.** A palette someone saved before the
  lock stays in their account, untouched. Remove `paletteLocked` and their own
  colors come back exactly as they were. That is deliberate: a lock you cannot
  safely trial is a lock nobody trials.
- **The lock alone does nothing.** `paletteLocked` without a `palette` is
  ignored, so a typo in the palette key cannot leave staff frozen on the
  packaged defaults with no way to edit them.
- **It applies live.** Toggling the policy takes effect on the next picker they
  open, with no browser restart. A popup or settings page already open when you
  toggle it switches itself over too — both subscribe to policy changes — though
  a picker already on screen updates on its next open rather than under the
  cursor.

### Testing the FORCE INSTALL path

Worth stating plainly, because it is the setting most real deployments will
use and it is the one the 0.2.0 test does NOT exercise.

**What is already covered.** The palette behavior cannot differ between force
and allow: the managed payload is delivered per extension ID, and no shipped
file reads `chrome.management` or `installType` (pinned by a static test). The
delivery mechanism itself is confirmed working in the field under Allow
install. So "does force install deliver the palette policy" is answered by
construction, not by hope.

**What is NOT covered, and why.** Nothing has watched the whole path run — a
managed browser force-installing this extension and receiving the policy —
because of a collision the ID pinning creates. `manifest.json` carries the Web
Store item's `key`, so the unpacked development build and the published build
share the ID `hchpnnppgakgmobkbldgkohmplkcahjl`. Force install therefore pulls
the STORE version down on top of whatever is loaded unpacked, and the store
version is 0.1.7 — a build without any of the behavior under test. Setting
force install today tests 0.1.7, not this tree.

**The two ways out**, neither of which should be chosen casually:

1. **Publish the build to the Web Store first**, then force install it. The
   Store supports restricting an item's visibility to your own Workspace
   domain, so this need not be a public release. Costs a version number (the
   Store never lets one be reused) and a review turnaround, and per `CLAUDE.md`
   nothing may be packaged without the in-browser smoke check first.
2. **Self-host the CRX** and add it by ID with an installation URL, which is
   what the console's *Add Chrome app or extension by ID* path is actually for.
   The extension would then be signed with a key we hold, so it gets its own
   stable ID and never collides with the store item. This also gives the
   self-hosted deployments described in `docs/REMOTE_CONFIG_DECISION.md` a real
   distribution channel. Larger build: a signed `.crx`, an update-manifest XML,
   and somewhere to serve both.

Tracked in bd; do not pick one without the product owner.

### Testing a policy WITHOUT a managed device (macOS) — DEVELOPERS ONLY

**Nothing in this subsection is an admin task.** It is a local rig for working
on this repo without a managed fleet, and it fakes on one machine what the
Admin console delivers over the network. An admin publishing colors uses the
console UI above (or `options/policy-builder.html` to build the payload),
never a terminal. Two consequences worth stating plainly, because both have
already cost a day in the field:

- The **release test goes through the console**, not through this script. The
  local mechanism shipped with a wrong recipe while real cloud policy was
  working the whole time, so a green local run proves nothing about the path
  users are on. See `docs/TESTING-0.2.0.md`.
- The plist this writes is **machine-wide** and applies to every Chrome profile
  on the Mac, including personal ones signed in to unrelated accounts. That is
  inherent to faking policy locally and is NOT how the extension behaves; real
  policy is scoped to the managed account (see "Where the extension stores
  things"). Clean up with `sudo dev/test-policy.sh none` when done.

The 0.1.7 managed palette shipped never having been exercised against a real
policy, because there was no way to set one outside a managed fleet. There is:
on macOS, Chrome reads an extension's managed storage from a per-extension
preference domain,
`/Library/Managed Preferences/com.google.Chrome.extensions.<EXTENSION_ID>.plist`,
with the policy keys (`palette`, `palettes`, `paletteLocked`) at the top level
of that file. The extension cannot tell this apart from a policy pushed by the
Admin console.

Two things the first version of this recipe got wrong, recorded so they are not
re-learned in the field: extension policy on macOS is **not** delivered through
`ExtensionSettings` in `com.google.Chrome.plist` (that shape belongs to the
Windows registry and the Linux JSON files — Chrome silently ignores it here,
and `chrome://policy` shows the extension's section with "No policies set"),
and hand-written XML plists in `Managed Preferences` are unreliable — write
binary. Never touch `com.google.Chrome.plist` itself; it may carry unrelated
machine policy (on the original test machine it force-installs another
extension entirely).

`dev/test-policy.sh` does all of this correctly, auto-detects the unpacked
extension's ID from Chrome's profile data, and has a mode per walkthrough step:

```bash
sudo dev/test-policy.sh unlocked      # palette only            (walkthrough step 3)
sudo dev/test-policy.sh locked        # + paletteLocked         (steps 4, 4b)
sudo dev/test-policy.sh multi         # several named palettes  (step 2b)
sudo dev/test-policy.sh lock-only     # degenerate: lock, no palette (step 7)
sudo dev/test-policy.sh degenerate    # degenerate: empty/invalid entries (step 7)
sudo dev/test-policy.sh none          # remove the policy       (steps 5, 8)
```

After each run: `chrome://policy` → **Reload policies**, and confirm the values
appear with status OK under the extension's section. If they do not appear,
quit Chrome fully (Cmd+Q) and reopen — Reload alone sometimes lags cfprefsd.
Verify what is actually on disk any time with:
`sudo plutil -p "/Library/Managed Preferences/com.google.Chrome.extensions.<ID>.plist"`.

This file is machine-wide and affects every Chrome profile on the Mac, so run
`sudo dev/test-policy.sh none` when you are done. On Linux the equivalent is a
JSON file in `/etc/opt/chrome/policies/managed/` using the `3rdparty` key,
which needs no cfprefsd step.

**Privacy.** Policy flows one way, into the browser. Nothing about the palette,
the user, or their documents is sent anywhere (see `docs/PRIVACY.md`).

## Where the extension stores things (and how far it reaches)

**Nothing the extension writes is machine-wide.** Everything is scoped to a
Chrome profile or to the Google account signed into it, and the only thing two
people ever share is what an administrator delivers to both of them.

That claim is checkable rather than asserted: **every storage read and write in
the extension goes through `lib/storage.js`**, so this table is the complete
list. The only `chrome.storage` reference outside that module is one
`onChanged` subscription in `background/service-worker.js` (the toolbar icon
repainting when the palette changes) — a listener, not another writer.

```
grep -rn "chrome\.storage\.\(sync\|local\|session\|managed\)\." \
  background content lib options popup shared config feedback | grep -v __tests__
```

| Key | Area | Scope | What it is |
| --- | --- | --- | --- |
| `pal:<id>` | sync | Google account | One stored palette (name + swatches), one item each |
| `paletteOrder` | sync | Google account | The order those palettes appear in |
| `activePaletteId` | sync | Google account | Which palette is in effect |
| `palette` | sync | Google account | Mirror of the active palette, for older builds and the live-update channel |
| `palettes` | sync | Google account | Retired single-key collection; migrated forward, then removed |
| `multiPalette` | sync | Google account | The Multiple palettes opt-in |
| `enforcementPushed` | sync | Google account | That an enforcement episode already moved this user once |
| `enabled` | sync | Google account | Legacy on/off flag; the toggle is retired from the UI and the worker heals a stranded `false` |
| `theme` | sync | Google account | Light / dark / system |
| `introSeen` | sync | Google account | First-run intro dismissed |
| `cachedSelectors` | local | Chrome profile, this machine | Cached remote selector contract |
| `cachedPalette` | local | Chrome profile, this machine | Cached remote palette |
| `paletteHistory` | local | Chrome profile, this machine | Popup undo/redo stack |
| `ratingPrompt` | local | Chrome profile, this machine | Rating-prompt bookkeeping |
| `lastHealth` | local | Chrome profile, this machine | Last inject/apply health result |
| `updateNoteVersion` | local | Chrome profile, this machine | Which version's post-update notice was shown |
| `errorBuffer` | session | Chrome profile, until the browser closes | Background-worker errors awaiting the feedback page |
| `palette`, `palettes`, `paletteLocked` | managed | Delivered by policy; **read-only** to the extension | The organization's colors and the enforcement flag |

What each area means in practice:

- **sync** — per **Google account**, and only within it. The same person signed
  in on two machines sees the same palettes; a second account on the same
  machine sees none of them. Chrome does the syncing; the extension only reads
  and writes keys.
- **local** — per **Chrome profile on this machine**. Deliberate for everything
  in the list above: a cached selector fix, an undo stack, and "this machine
  has already shown you the update notice" are all machine-shaped facts, and a
  rating prompt that syncs would re-prompt on a second machine after being
  dismissed on the first.
- **session** — cleared when the browser closes.
- **managed** — arrives only where enterprise management delivers it: a
  managed account, or a managed browser. The extension can only READ it, which
  is exactly why organization colors are set in the Admin console and not
  inside the extension.

**Two accounts see the same colors only when an administrator publishes them
to both.** There is no other path: no shared storage, no server the extension
writes to, no device-level file.

**The single exception is developer test tooling, not the extension.**
`dev/test-policy.sh` writes
`/Library/Managed Preferences/com.google.Chrome.extensions.<ID>.plist`, which
macOS applies to **every Chrome profile on that Mac** — so while it exists, a
personal profile on the same machine also shows the test organization palette.
That is the local fake, behaving as macOS makes it behave; real Admin-console
policy is scoped to the managed account. Remove it with
`sudo dev/test-policy.sh none` and confirm with `ls` that the file is gone.

**Open decision (for the product owner):** per-account sync of personal
palettes is the current behavior and the current intent — the same person's
palettes follow them between machines. If palettes should instead be per
profile, never syncing, that is a `storage.local` migration and a separate,
larger piece of work. Tracked as bd `workspace-custom-palette-td0`.

## Monitor (synthetic checks)

See `monitor/README.md`. One-time: `npm install`, `npx playwright install

`npm run monitor` via systemd timer / cron / GitHub Actions; set

## Fixing a broken selector (no repackage)

Google changes its DOM → monitor goes red → GitHub issue with a diagnostic
bundle. Correct the selector in `service/data/selectors.json` (or `POST
/config/selectors` with the fixed contract).

**This reaches only clients whose build sets `CONFIG_BASE` to this server.**
Those pick it up on their next refresh (`REFRESH_PERIOD_MINUTES`), with no Web
Store round trip. Web Store installs ship `CONFIG_BASE` empty, run on the
packaged fallback, and need a release: correcting the served file does nothing
for them. See `docs/REMOTE_CONFIG_DECISION.md`. Check which you are looking at
before reaching for this section during an incident.

**Close the issue yourself once the monitor is green.** Auto-close is not wired
up: the recovery branch exists but no caller reaches it. Also delete the failure
signature from `service/monitor-results/alerts-state.json`, or the next occurrence of
the same failure will comment "Still failing" on the issue you just closed
instead of opening a fresh one. See `service/README.md` for the detail and bd
`workspace-custom-palette-ykj` for the open decision.
